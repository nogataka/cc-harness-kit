# ハーネス構築の司令塔

対象: `$ARGUMENTS`（空ならカレントディレクトリ。対象リポで `claude` を起動するディレクトリです）

このスキルは自分では書き込みません。現状を採点し、次に実行するスキルを1つ案内して終わります。各層のスキルはそれぞれが「探索→提案書→承認→書込」で動くので、1層ずつ確認しながら進められます。

## 手順

### 1. 監査する

Skill ツールで `harness-audit` を呼び、採点表を得ます。引数には上の対象ディレクトリを渡します。

### 2. 起動ディレクトリを確定する

採点表の前に、人に1つだけ確認します。

> このリポでは、どのディレクトリから `claude` を起動する運用にしますか。（推奨: 作業するパッケージのディレクトリ。複数パッケージをまたぐ作業が多いならルート）

答えによって設定ファイルの置き場所が変わります（`.claude/settings.json` は親から継承されません）。「ルートから起動せざるを得ない」という答えだった場合は、その旨を `/harness-claudemd` への案内文に添えます。他チームや触らない領域の CLAUDE.md を `claudeMdExcludes` で除外する案を、`harness-claudemd` の提案書で検討してもらうためです。答えを以降のスキルへの案内文に含めます。

### 3. 次の1層を案内する

採点表で「未着手」または「一部」の層を、次の順で最初に見つかったものだけ案内します。

| 順 | 層 | 案内するスキル | 案内文に含めること |
|---|---|---|---|
| 1 | 第1層 CLAUDE.md | `/harness-claudemd` | 超過ファイル数、強い語・手順・重複の行数 |
| 2 | 除外 | `/harness-exclusions` | `.claudeignore` の警告、候補ディレクトリ |
| 3 | 第2層 フック | `/harness-hooks` | 起動ディレクトリ |
| 4 | 第3層 スキル | `/harness-skills` | CLAUDE.md に残る手順の行数 |
| 5 | 第5層 LSP | `/harness-lsp` | 検出言語とバイナリの有無 |
| 6 | 第4層 プラグイン | `/harness-plugin` | チームで共有するかどうか |
| 7 | オーナーシップ | `/harness-ownership` | DRI の候補 |

除外を第1層の直後に置くのは、読み取り拒否を先に入れておくと以降の探索でノイズが減るためです。LSP をプラグインより先に置くのは、LSP の有効化がそのまま最初の `enabledPlugins` になり、プラグイン層で扱う具体的なもの（社内マーケットプレイスの登録、チーム共有可否の判断）ができてから案内する方が分かりやすいためです。第6層 MCP と第7層 サブエージェントは専用スキルを持たず、採点表の情報を伝えるだけにします。

案内は次の形で1つだけ書きます。

> 次は `/harness-claudemd <起動ディレクトリ>` を実行してください。理由: <採点表の該当行の根拠>。

各層のスキルは人が起動するものです。Skill ツールで呼ばず、必ず人に案内してください。

### 4. すべて充足していたら

採点表に「未着手」「一部」が無ければ、次を伝えて終わります。

- 次回の構成レビュー日（`docs/agents/harness-owner.md` に記録されているもの）
- `.claude/harness-kit/claudemd-candidates.md` に追記候補が溜まっていれば、その件数
- 提案書（`harness-proposal-*.md`）が残っていれば、消してよいこと

## 後始末の案内

提案書ファイルは承認後に不要です。対象リポの `.gitignore` に次の2行を足す提案を、最初の層の案内に添えます。

```
harness-proposal-*.md
.claude/harness-kit/backup/
```
